## 1. 문제 정의

### 1-1. 폴더가 없어 "정리"와 "문서"가 뒤섞인다

현재 계층은 `Page.parentId` 하나뿐이라, **묶기 위한 껍데기**와 **읽기 위한 문서**가 구분되지 않는다. 목차 역할만 하는 페이지도 본문·버전·댓글을 갖고, 트리에서 문서와 똑같은 아이콘으로 보인다. 사용자는 "이건 폴더인가 문서인가"를 제목으로 추측해야 한다.

레퍼런스는 폴더를 **별도 콘텐츠 타입**으로 두고, 폴더를 열면 본문 대신 **자식 목록 테이블**을 보여준다.

### 1-2. 편집 중인 문서의 상태가 화면에 없다

현재 편집 화면에는 저장 상태 표시가 없고, 사이드바에서 초안(아직 게시되지 않은 문서)을 구분할 방법이 없다. 레퍼런스는 상단 바에 `저장됨`을, 트리 항목에 `초안` 배지를 노출한다.

### 1-3. 한 줄에 두 가지를 나란히 놓을 수 없다

본문이 단일 세로 흐름뿐이라 "좌: 설명 / 우: 예시" 같은 배치가 불가능하다. → **레이어 분할(컬럼)**.

### 대상 사용자

사내 위키에 문서를 쌓는 팀원(작성자·열람자). 관리자 전용 기능은 이번 범위 밖.

### 성공 기준 (목업 단계 — 실사용 지표 대신 검증 가능한 완료 기준)

| # | 기준 |
|---|---|
| S1 | 사이드바 "만들기"에서 폴더를 만들고, 그 폴더로 페이지를 옮기고, 폴더 화면에서 자식 목록을 확인하는 흐름이 끊김 없이 완주된다 |
| S2 | 폴더는 트리·폴더 화면·스페이스 개요 세 곳에서 문서와 시각적으로 구분된다(아이콘 + 텍스트 둘 다 — 색·아이콘만으로 구분하지 않는다) |
| S3 | 편집 화면에서 저장 상태가 항상 보이고, 미게시 문서는 트리에서 `초안`으로 식별된다 |
| S4 | 2열/3열 레이아웃을 만들고 저장 후 다시 열었을 때 구조가 그대로 복원된다(마크다운 왕복 무손실) |

### 범위 — 포함 / 명시적 제외

**포함**
- 폴더 콘텐츠 타입(생성·이름변경·삭제·이동), 폴더 상세 화면, 트리 통합
- 콘텐츠 타입 선택 "만들기" 메뉴
- 편집 화면 상단 크롬 정비(저장 상태) + `초안` 배지
- 레이어 분할(2·3열)

**제외 (이번에 만들지 않는다)**
- 라이브 문서 · 화이트보드 · 데이터베이스 · 스마트 링크 — 캡처의 만들기 메뉴에 있으나 각각 별도 대형 기능이다. 메뉴에 **비활성 항목으로도 넣지 않는다**(되지 않는 컨트롤 노출 금지).
- 폴더 배너 이미지(캡처의 파란 일러스트) — 파일 스토리지 선행. 단색 배경으로 대체.
- 폴더별 권한, 폴더 안의 폴더 정렬 커스터마이즈
- "공동 작업자" 열의 실제 데이터 — 백엔드 미제공(§6)
- ~~3열 초과 레이아웃~~ → **뒤집힘 (2026-08-03)**: 당시 레퍼런스에 없어서 잘랐는데, 새 캡처
  (`레이아웃.png`)가 1~5열을 보여준다. [편집기 요소 심화 기획](2026-08-03-editor-elements-depth.md) §3 A1로 이관

## 2. 유저스토리 · 인수조건

### Activity A. 콘텐츠 구조 정리 (폴더)

**A1. 폴더 만들기** *(Must)*
> 작성자로서, 관련 문서를 묶을 폴더를 만들어 트리를 정돈하고 싶다.

```
Given 스페이스 사이드바를 보고 있고
When "만들기"에서 "폴더"를 선택하면
Then 새 폴더가 트리에 폴더 아이콘으로 나타나고 그 폴더 화면으로 이동한다
```
```
Given 새로 만든 폴더의 이름이 비어 있을 때
When 폴더 화면에서 이름을 입력하고 확정하면
Then 트리와 폴더 화면의 이름이 함께 갱신된다
```

**A2. 폴더 화면에서 자식 보기** *(Must)*
> 열람자로서, 폴더를 열면 그 안에 무엇이 있는지 목록으로 보고 싶다.

```
Given 자식이 있는 폴더를 열었을 때
Then 이름·마지막 편집·작업 열을 가진 표로 자식 목록이 보이고
And 이름을 클릭하면 해당 문서/폴더로 이동한다
```
```
Given 자식이 없는 폴더를 열었을 때
Then 비어 있음을 알리고 "페이지 만들기" 같은 다음 행동을 제시한다
```

**A3. 트리에서 폴더 구분·펼치기** *(Must)*
> 열람자로서, 트리에서 폴더와 문서를 한눈에 구분하고 싶다.

```
Given 사이드바 트리에 폴더와 페이지가 섞여 있을 때
Then 폴더는 폴더 아이콘 + 펼침 토글로, 페이지는 문서 아이콘으로 표시된다
```

**A4. 폴더로 옮기기 / 폴더 삭제** *(Should)*
```
Given 페이지를 폴더 안으로 드래그하면
Then 그 페이지가 폴더의 자식이 되고 트리·폴더 화면에 함께 반영된다
```
```
Given 자식이 있는 폴더를 삭제하려 할 때
Then 하위 항목 개수와 함께 처리 방식(상위로 올리기 / 함께 삭제)을 묻고, 고른 뒤에만 삭제된다
```

### Activity B. 편집 화면 구조

**B1. 저장 상태 표시** *(Must)*
```
Given 편집 화면에서 내용을 바꿨을 때
Then 상단 바에 저장 상태(저장됨 / 저장되지 않은 변경)가 보인다
```

**B2. 초안 만들기 → 게시** *(Must — 2026-07-26 승격)*
> 작성자로서, 일단 빈 문서를 만들어 두고 다 쓴 뒤에 공개하고 싶다.

```
Given 스페이스 사이드바의 콘텐츠 "+"를 누르면
Then 초안 문서가 즉시 만들어져 트리에 "초안" 배지와 함께 나타나고 편집 화면이 열린다
```
```
Given 초안을 편집 중일 때
Then 주 액션이 "업데이트"가 아니라 "게시"이고, 게시하면 배지가 사라진다
```

### Activity C. 레이어 분할

**C1. 열 나누기** *(Must)*
```
Given 편집 중 삽입 메뉴에서 "레이어 분할"을 고르고 열 수를 선택하면
Then 본문에 빈 열들이 생기고 첫 열에 커서가 놓인다
```
```
Given 각 열에 내용을 넣고 저장한 뒤 다시 편집 화면을 열면
Then 열 구성과 내용이 그대로 복원된다
```

**C2. 보기 화면 렌더 · 좁은 화면 대응** *(Must)*
```
Given 열이 있는 문서를 보기 화면에서 열면
Then 편집 화면과 같은 열 배치로 렌더된다
And 화면이 좁으면 열이 세로로 쌓여 가로 스크롤이 생기지 않는다
```

## 3. 우선순위 (MoSCoW)

실사용 데이터가 없는 목업 단계이므로 RICE는 쓰지 않는다(가짜 정밀도 방지).

| 스토리 | 등급 | 근거 |
|---|---|---|
| C1·C2 레이어 분할 | **Must** | 저장 포맷 결정이 이미 끝났고(§5) 파이프라인 왕복도 실증됨 — 가장 짧은 경로 |
| A1 폴더 만들기 | **Must** | 이후 모든 폴더 스토리의 전제 |
| A2 폴더 화면 | **Must** | 폴더를 만들어도 볼 화면이 없으면 흐름이 완주되지 않는다 |
| A3 트리 구분 | **Must** | S2의 핵심. 이게 없으면 폴더를 만든 의미가 화면에 드러나지 않는다 |
| B1 저장 상태 | **Must** | 작고 독립적, 편집 신뢰도에 직접 기여 |
| A4 이동·삭제 | Should | 기존 DnD·삭제 흐름 확장 |
| B2 초안 만들기 → 게시 | **Must** | 2026-07-26 사용자 확정 — P3 결정과 함께 승격 |
| 배너 이미지·공동 작업자 열·권한 | **Won't** | 백엔드/스토리지 선행 (§1 제외) |

**MVP(수평 슬라이스)** = C1 + C2 + A1 + A2 + A3 + B1 + B2
→ "폴더를 만들어 문서를 정리하고, 문서 안에서는 열을 나눠 쓰고, 저장 상태를 확인한다"가 한 번 완주된다.

## 5. 확정된 결정 — 레이어 분할 저장 포맷

로드맵의 `⚠️ 저장 포맷 재논의` 플래그(3단계, 마크다운 비표현 블록)에 걸리는 항목이었고, **확장 문법(`:::`)** 으로 결정했다. 블록 JSON 전환은 채택하지 않는다.

```
::::columns
:::column
왼쪽 내용
:::
:::column
오른쪽 내용
:::
::::
```

- `Page.body`는 계속 마크다운 문자열 → 백엔드 계약·버전 diff·`[[링크]]` 파이프라인 무변경 (CLAUDE.md 불변조건 2 유지)
- 중첩은 "바깥 마커가 더 길다" 규칙(markdown-it-container·remark-directive 공통 관례)
- **대가**: GFM 표준이 아니므로 이 문법을 모르는 렌더러에서는 `:::` 줄이 텍스트로 보인다. 내용은 사라지지 않는다.
- 편집(markdown-it 컨테이너 규칙)과 보기(remark-directive) 두 경로가 같은 문자열을 같은 구조로 읽어야 한다 — 한쪽만 바꾸지 않는다.

## 6. 열린 정책 결정

| # | 항목 | 플래그 |
|---|---|---|
| P1 | ~~폴더를 `Page`의 타입 필드로 표현할지, 별도 엔티티로 둘지~~ → **결정(2026-07-26): `Page.type: "page" \| "folder"`.** 기존 `parentId` 계층·트리·`movePage`·store 함수를 그대로 재사용해 변경 범위가 가장 작고, 백엔드도 컬럼 하나만 추가하면 된다. 대가로 폴더가 `body`·버전·댓글 필드를 형식적으로 갖게 되며(P4와 연결), 폴더에서는 그 필드를 쓰지 않는다는 것을 화면·스토어 계약으로 강제한다 | ✅ 확정 |
| P2 | ~~자식이 있는 폴더 삭제 시 처리(같이 삭제 / 부모로 승격)~~ → **결정(2026-07-28): 삭제 시점에 사용자가 고른다.** 막지 않는다 — 삭제 다이얼로그가 하위 항목 개수를 알려주고 `상위로 올리기`(기본값) / `함께 삭제` 중 하나를 고르게 한다. 기본값이 파괴가 덜한 쪽인 이유는 확인을 연타하는 사용자가 하위 문서를 통째로 잃지 않아야 하기 때문이다. 폴더와 페이지에 같은 규칙을 적용한다(체크리스트 §2의 페이지 삭제 정책도 이 결정으로 함께 닫힌다) | ✅ 확정 |
| P3 | ~~"초안" 개념을 실제로 도입할지~~ → **결정(2026-07-26): 도입.** `Page.status: "draft" \| "published"`. 사이드바 콘텐츠 "+"가 초안을 즉시 만들어 트리에 `초안` 배지와 함께 세우고, 편집 화면의 주 액션이 "업데이트" 대신 "게시"가 된다. 기존 문서·기존 저장 흐름은 그대로(저장=즉시 반영) — 초안에만 게시 단계가 붙는다. 폴더는 게시 개념이 없어 항상 published | ✅ 확정 |
| P4 | 폴더에 본문·댓글·버전을 허용할지(레퍼런스는 목록만) | ❓ 정책대기 |
| P5 | "공동 작업자" 열 데이터 출처 — 백엔드가 편집 참여자 목록을 주는지 | ❓ 정책대기 |

**백엔드 계약 — 완료(2026-07-28)**: wiki-backend V2가 `page.type`·`page.status` 컬럼과 `POST /api/wiki/pages/{id}/publish`를 제공한다. 어댑터의 세 지점(`createPage` 요청 필드 · `mapPage`/`mapPageTree` 응답 · `publishPage`)을 실제 계약으로 교체했다 — 목업 전용 기능이 아니다. 폴더는 게시 개념이 없어 draft로 요청해도 서버가 published로 고정한다.
