> **"컨플루언스를 쓰던 사람이 우리 위키에 와서 없다고 느낄 기능"**만 제품 기능 단위로 재정리했다.

## 1. 결론

에디터·실시간 공동 편집·페이지 제한은 컨플루언스 수준에 도달했다. 남은 격차는 **문서를 쓰는 기능이 아니라
문서를 관리하는 기능**에 몰려 있다. 지우면 복구할 수 없고, 분류할 수단이 없고, 이미지 외의 파일을 붙일
화면이 없고, 밖으로 꺼낼 방법이 없다.

우선순위 상위 4개 묶음을 이번 스프린트(W21) 범위로 확정했다.

| 묶음 | 왜 먼저인가 |
|---|---|
| 휴지통·복원·보존 | 유일하게 **되돌릴 수 없는** 결함이다. 나머지는 없어도 데이터가 사라지지 않는다 |
| 라벨 + 백링크 | 문서가 수백 건이 되는 순간 트리만으로는 못 찾는다. 검색 필터 확장의 선행 조건 |
| 첨부파일 관리 + 내보내기 | 지금은 이미지 말고는 파일을 올릴 화면이 없고, 내용을 꺼낼 경로가 전혀 없다 |
| 인라인 댓글 + watch | 컨플루언스 협업의 기본 단위. 페이지 댓글만으로는 "이 문장"을 가리킬 수 없다 |

## 4. W21 스프린트 범위 — 인수조건

### W21-1 휴지통·복원·보존

- 페이지 삭제는 소프트 삭제다. 본문·리비전·댓글·첨부 객체가 남는다.
- `children=cascade` 삭제는 하위를 함께 휴지통으로 보내고, 복원은 그 묶음을 함께 되살린다.
  독립적으로 먼저 버려진 하위 묶음은 함께 복원되지 않는다.
- 휴지통 목록은 스페이스 단위로 보이고, 사용자가 직접 버린 항목만 행으로 뜬다(하위는 개수로 표시).
- 부모가 사라진 뒤 복원하면 루트로 올라오고, 그 사실을 사용자에게 알린다.
- 영구 삭제와 휴지통 비우기는 스페이스 ADMIN만 할 수 있다.
- 삭제된 페이지는 트리·검색·첨부·댓글·알림·링크 어디에서도 보이지 않는다.
- 보존 기간(`platform.wiki.trash.retention`)이 설정되면 그 기간이 지난 항목을 자동으로 영구 삭제한다.
  기본값은 자동 삭제 없음이다.

### W21-2 라벨 + 백링크

- 페이지에 라벨을 붙이고 뗄 수 있고, 편집 권한이 있는 사람만 바꿀 수 있다.
- 스페이스의 라벨 목록과 라벨별 페이지 목록을 볼 수 있다.
- 라벨은 검색 결과에서 필터로 쓸 수 있다. (→ §4-1: search-service 색인이 선행이라 이번 범위에서 제외)
- 본문의 `[[페이지]]` 내부 링크는 저장 시 역방향으로 기록되고, 페이지 하단에 "이 페이지를 링크한 문서"로 보인다.
- 페이지를 삭제·복원하면 백링크 목록이 그에 맞게 바뀐다.

### W21-3 첨부파일 관리 + 내보내기

- 페이지에 첨부파일 탭이 있고, 본문에 넣지 않은 파일도 올릴 수 있다.
- 목록에서 파일명·형식·크기·올린 사람·시각을 보고 내려받거나 지울 수 있다.
- 지울 때는 본문이 그 파일을 참조 중이면 경고한다.
- 페이지를 Markdown·HTML로 내보낼 수 있고, 하위 포함 여부를 고를 수 있다.
- 내보낸 HTML은 이미지가 포함되어 오프라인에서도 열린다.

### W21-4 인라인 댓글 + watch

- 본문 텍스트를 선택해 댓글을 달 수 있고, 그 구간이 하이라이트로 표시된다.
- 스레드를 해결하면 하이라이트가 사라지고, 다시 열 수 있다.
- 본문이 바뀌어 앵커 텍스트를 못 찾으면 스레드는 사라지지 않고 "위치 없음"으로 남는다.
- 페이지를 구독·해제할 수 있고, 구독자는 수정·댓글 알림을 받는다.
- 페이지를 만들거나 수정하면 자동으로 구독되며, 사용자가 해제할 수 있다.

## 4-1. 구현 결과 (2026-08-28)

네 묶음 모두 백엔드·프론트 양쪽을 구현하고 게이트를 통과했다.
검증: wiki-backend 204 테스트(실제 PostgreSQL Flyway V1→V15 검증 포함), wiki-front 809 테스트 +
`pnpm typecheck` + production build.

| 묶음 | 백엔드 | 프론트 |
|---|---|---|
| W21-1 휴지통 | V13 소프트 삭제(`@SQLRestriction`), `TrashService`(목록·복원·영구삭제·비우기), 보존 기간 스케줄러 | `/spaces/:id/trash` 화면, 사이드바 진입점 |
| W21-2 라벨·백링크 | V14 `page_label`·`page_link`, 저장 시 링크 재색인 | 페이지 하단 라벨 칩, 백링크 섹션, `/spaces/:id/labels` |
| W21-3 첨부·내보내기 | 변경 없음(업로드 API가 이미 CONFIRMED로 저장) | 첨부 목록·업로드·삭제 UI, Markdown/HTML 내보내기 |
| W21-4 인라인 댓글·구독 | V15 앵커·해결 상태·`page_watch`, 알림 대상을 구독 원장으로 이관 | 본문 하이라이트·스레드 패널, 구독 토글 |

### 설계에서 조정한 것

- **인라인 앵커는 렌더된 본문 기준이다.** 처음엔 서버가 마크다운 원문과 대조하려 했으나,
  서식을 가로지르는 선택(`배포는 **금요일**에`)은 원문에 그대로 없어 정당한 선택을 거부한다.
  서버는 앵커를 보관만 하고 위치 찾기는 렌더러가 한다.
- **PDF 내보내기는 브라우저 인쇄로 넘겼다.** 자체 렌더러 없이 만든 PDF는 표·코드 블록이 화면과
  어긋나 신뢰를 깎는다. Markdown(무손실)·HTML(이미지 내장)만 파일로 낸다.
- **알림 대상 모델을 교체했다.** "작성자 + 편집자" 계산식은 끌 수가 없어 `page_watch` 원장으로
  옮겼다. 기존 사용자는 V15 백필(프론트는 `normalize`)로 승계된다.
- **검색의 라벨 필터는 아직 없다.** 검색 색인은 별도 서비스(search-service)라 라벨을 색인해야
  한다. 위키 안의 라벨 탐색(`/labels`)까지가 이번 범위다.

## 5. 이번 범위 밖으로 남기는 것

| 항목 | 이유 |
|---|---|
| 블로그·개인 스페이스 | 콘텐츠 타입 추가는 트리·검색·권한을 모두 건드린다. 별도 웨이브 |
| 페이지 템플릿 | 라벨·내보내기보다 요구가 약하고, 블루프린트까지 가면 범위가 크다 |
| 감사 로그 | org-service 확장이 선행 |
| 첨부 버전·미리보기 | 첨부 화면이 먼저 있어야 필요가 드러난다 |
| 리액션·공유·작업 목록 | 협업 2차 |
| 애드온 플랫폼 | ADR 선행(갭 분석 §5.6) |

## 6. 규모 대응 (2026-08-29)

"문서량이 2TB면 버티는가"에서 시작한 작업. 용량 자체보다 **요청당 비용이 스페이스 크기에
비례하는 지점**이 먼저 무너진다고 판단해 그 세 곳을 순서대로 잡았다.

### 6.1 권한 판정 — 완료

제한 판정이 요청마다 스페이스의 전 페이지로 부모 맵을 만들고 있었다. 페이지 한 장을 여는
비용이 스페이스 크기에 비례했다는 뜻이다.

대상의 **조상 폐포만** 읽도록 바꿨다(재귀 CTE 1쿼리 + 그 id들의 제한 행). 스페이스 전량이
정말 필요한 곳은 트리 필터 하나뿐이라 거기만 남겼다. 캐시를 쓰지 않은 것은 의도다 —
제한·트리 변경 직후의 스테일 인덱스는 그대로 누출이라, 무효화가 완벽해야만 안전한 캐시보다
질의를 싸게 만드는 쪽을 택했다.

회귀 가드: `PermissionQueryScaleTest` — 5페이지 스페이스와 300페이지 스페이스의 조회 질의
수가 같아야 한다(Hibernate statistics).

### 6.2 리비전 보존 — 완료 (정책: 전부 보관 + 압축)

저장할 때마다 본문 전체가 새 리비전으로 복사된다. 이력을 지우지 않기로 했으므로 남은 수단은
크기를 줄이는 것뿐이다.

V16에서 gzip 압축본을 BYTEA에 담고 `STORAGE EXTERNAL`로 TOAST의 이중 압축을 막았다.
512자 미만은 gzip 헤더 때문에 오히려 커져 평문으로 둔다. 기존 행은 그대로 두고 엔티티가 둘 중
있는 쪽을 읽으므로 일괄 변환이 필요 없다.

### 6.3 트리·전체목록 지연 로딩 — 완료 (전면 리팩터)

**끝난 것 (백엔드):** 화면 단위 조회 API 5종 — 직계 자식(`childCount` 포함), 조상 체인,
후손 폐포, 제목 정확 조회, 제목 부분 검색. 전부 effective VIEW로 걸러 나가고, 누출 테스트가
다섯 경로를 모두 덮는다(`TreeApiTest`).

**끝난 것 (프론트 소비처 이관):**

| 소비처 | 이전 | 지금 |
|---|---|---|
| `[[제목]]` 링크 해석 | 스페이스 전 페이지에서 제목 색인 | 본문에 등장한 제목만 조회 |
| `[[` 자동완성 | 전 페이지 필터 | 서버 제목 검색(빈 질의는 최상위 문서) |
| 링크 칩 존재/부재 | 전 페이지 | 문서에 등장한 제목의 조회 결과 캐시 |
| 붙여넣기 링크 메뉴 | 전 페이지에서 id 조회 | URL에서 id만 뽑고 제목은 서버 조회 |
| 공동 편집 세션 | 전 페이지 배열 보유 | 편집 화면과 같은 링크 캐시 공유 |
| 하위 페이지 목록 | 전 페이지 필터 | 직계 자식 조회 |
| 내보내기(하위 포함) | 전 페이지에서 서브트리 계산 | 후손 폐포 조회 + 클라이언트 정렬 |

**끝난 것 (트리 뒤집기, 2026-08-29):**

- `useSpaceTree` — 최상위만 먼저 받고 펼칠 때 한 단계씩 받는다. 접었다 펴는 것은 재요청하지
  않고, 생성·이동·삭제 후에는 **펼쳐 둔 자리만** 다시 읽는다.
- `PageTree` 기본값이 "펼침"에서 **"접힘"**으로 바뀌었다. 화살표는 서버가 준 `childCount`로
  그린다 — 자식을 받아보기 전에 알아야 하기 때문이다.
- 깊은 링크(`/pages/손자`)로 들어오면 조상 체인을 받아 그 자리까지 펼친다. 트리를 다 받지
  않으므로 펼쳐 주지 않으면 현재 위치가 사이드바에 나타나지 않는다.
- 사이드바 제목 검색이 서버 검색이 됐고 결과는 **평면 목록**이다. 매치마다 조상 체인을 따로
  받아오면 한 번 타이핑에 요청이 수십 개가 된다.
- 별표 스냅샷 최신화는 별표된 id만 서버에 묻는다(`/pages/by-ids`). 로드된 노드만으로 맞추면
  접힌 가지의 별표 제목이 조용히 낡는다.
- `WikiOutletContext`에서 `pages`가 사라졌다 — "스페이스의 전 페이지"라는 것이 화면에 더는
  존재하지 않는다.

**의도한 동작 변경**

| 이전 | 지금 | 이유 |
|---|---|---|
| 사이드바가 전부 펼쳐진 상태로 시작 | 최상위만, 펼치면 로드 | 전량 로드가 곧 규모 상한이었다 |
| 검색이 매치 + 조상 체인을 트리로 유지 | 매치만 평면 목록 | 조상 체인을 매치마다 받으면 요청이 폭증한다 |

### 6.4 부채 정리 (2026-08-29)

| 항목 | 처리 |
|---|---|
| 스페이스 개요가 전량 조회 | **해결.** 개요는 최상위 목록 + 최근 업데이트(전용 조회)만 읽는다. 전체 계층을 한 화면에 펼치는 것은 그만뒀다 — 조망은 "무엇이 있는지"까지면 충분하고, 그 아래는 사이드바 트리와 각 문서가 맡는다 |
| 이동 다이얼로그가 대상 스페이스 전량 조회 | **해결.** 컨플루언스처럼 "쳐서 찾는" 위치 선택으로 바꿨다(검색어 없으면 최상위). 만들기 다이얼로그의 상위 위치 선택도 같다 |
| 레거시 전체 트리 API | **제거.** `GET /spaces/{id}/pages`와 `listPages`를 양쪽에서 지웠다. 인증된 사용자면 누구나 스페이스 전량을 끌어올 수 있는 무제한 질의가 API 표면에서 사라졌다 |
| 테스트 전용 리포지토리 메서드 | **제거.** 휴지통 포함 전량 삭제는 테스트 헬퍼(`TestPages`)로 옮겼다 — 운영 코드에 그런 수단이 존재하지 않아야 한다 |
| 초기 JS chunk | **완화.** 편집 화면을 지연 로딩해 1.56MB → 1.20MB(gzip 509KB → 377KB). 편집기 청크 359KB는 읽기만 하는 사용자가 받지 않는다 |
| 검색 결과의 계층 | **남김.** 평면 목록이라 "어느 폴더 아래인지"가 보이지 않는다. 경로 라벨을 붙이려면 매치마다 조상 조회가 필요해 비용 대비 이득을 더 봐야 한다 |

전량 조회가 남은 곳은 이제 없다. 테스트가 상태를 통째로 확인해야 할 때는 지연 트리 API를
재귀로 훑는 헬퍼(`allPagesForTest`)를 쓴다 — 운영 경로에는 같은 수단이 없다.

## 7. W22 — 버전 이력 완성 (2026-08-29)

이전 한계 둘을 닫았다. 비교가 직전 버전에 고정돼 있었고, 이력에 "무엇을 왜 고쳤는지"가 없어
버전이 쌓이면 어느 것이 되돌릴 지점인지 알 수 없었다.

- **변경 요약(V17)** — 저장할 때 한 줄을 남기면 그 버전의 이력에 붙는다. **선택 입력**이다:
  강제하면 "수정"만 적힌 이력이 쌓여 오히려 신호가 죽는다. 공백만 적은 요약은 없는 것으로 눕힌다.
- **복원 자동 기록** — 복원이 만드는 새 버전에는 "vN 버전으로 복원"이 남는다. 어느 버전에서
  되돌렸는지가 다음 사람에게 가장 중요한 정보다.
- **임의 두 버전 비교** — 히스토리에서 비교 기준을 고른다. 기본값은 종전대로 직전 버전.
- **버전 본문 단건 조회** — 목록은 메타만 준다. 여기서 실측 결함을 하나 잡았다: 백엔드 모드의
  버전 목록은 본문을 담지 않는데 미리보기·diff가 그 목록의 `body`를 그대로 읽고 있어 **빈 화면**이
  나왔다. 화면에 필요한 두 버전만 단건으로 읽어 캐시한다.

부수 수정: 편집 화면 지연 로딩 이후 편집 관련 테스트가 간헐적으로 5초 예산을 넘겼다(동적 import가
테스트당 예산 안에서 일어났다). 테스트 하네스가 모듈을 미리 데운다 — 앱 동작은 그대로다.

## 8. W22 — 스페이스 설정 (2026-08-29)

백엔드에 이름 변경·삭제 API가 있는데도 **화면 진입점이 없어** 한번 만든 스페이스는 이름도 못
고치고 지울 수도 없었다. 사이드바 하단에 설정을 두고 세 탭으로 묶었다.

- **일반** — 이름·설명 수정.
- **권한** — org-service grant를 직접 다룬다. 사용자/팀 × 보기·편집·관리.
- **삭제** — 되돌릴 수 없음을 글로도 알리고 확인 다이얼로그를 받는다.

### org-service 권한 범위를 넓혔다

grant API가 **전역 관리자만** 허용하고 있어, 스페이스 소유자가 자기 공간에 사람을 초대할 수
없었다. `requireResourceAdmin`을 추가해 **그 리소스의 ADMIN**도 관리할 수 있게 했다.
컨플루언스도 스페이스 관리자가 그 스페이스 권한을 관리한다.

경계는 그대로 지킨다 — 스페이스 ADMIN이라도 다른 스페이스나 GLOBAL 권한은 만지지 못하고,
EDITOR는 자기가 속한 스페이스라도 권한을 볼 수 없다. 회수는 대상 grant를 먼저 읽어
"그 리소스의 관리자인가"를 물은 뒤에 지운다.

권한 목록 조회가 403이면 화면은 그 사실을 그대로 보여준다. 빈 목록으로 덮으면 "권한이 없는
건지 아무도 없는 건지"를 구분할 수 없다.

## 9. W22 — 검색 필터 (2026-08-29)

검색을 스페이스·문서종류로만 좁힐 수 있어 "누가 쓴 것", "최근 것"을 찾을 수 없었다.

색인에 이미 `authorId`·`updatedAt`이 있어 **질의만** 붙이면 됐다. 필터는 URL에 남긴다 —
걸러진 결과를 그대로 공유·북마크할 수 있어야 하고, 뒤로 가기가 필터를 잃으면 처음부터 다시
좁혀야 한다. 필터를 바꾸면 1페이지로 돌아간다(5페이지에서 좁히면 빈 화면만 보인다).

기간 경계는 포함이다. 날짜만 주면 그 날의 시작으로 읽는다. 형식이 잘못되면 조용히 무시하지
않고 거부한다.

### 라벨 필터 (같은 날 이어서)

라벨은 작성자·기간과 달리 색인에 없던 필드라 리포 세 개를 함께 고쳐야 했다.

| 곳 | 변경 |
|---|---|
| common-proto | `PageContent.labels`(13) 추가 — space_key처럼 딸려 보내 페이지마다 되묻지 않는다 |
| wiki-backend | gRPC 응답에 라벨을 싣는다. 목록 경로는 한 번에 모아 읽어 N+1을 만들지 않는다 |
| wiki-backend | 라벨을 바꾸면 그 페이지를 재색인한다 — 라벨이 색인 문서의 일부가 됐기 때문이다 |
| search-service | `labels` keyword 필드 + terms 필터(여럿이면 OR) |
| wiki-front | 검색 화면 라벨 입력(쉼표 구분), URL `labels=` |

질의도 저장할 때와 같은 규칙(소문자·공백→하이픈)으로 정규화한다. 대소문자만 달라서 안 걸리면
사용자는 이유를 알 수 없다.

라벨 입력만 **제출할 때** URL에 반영한다. 자유 입력이라 키 하나마다 검색을 쏘면 "설계"를 치는
동안 요청이 두 번 더 나간다.

**배포 절차:** 매핑이 `dynamic: strict`라 기존 인덱스에 라벨이 그냥 들어가지 않는다. 새 이미지를
올린 뒤 `POST /api/search/admin/reindex`(전역 관리자)를 한 번 돌려야 새 세대 인덱스가 만들어지고
별칭이 넘어간다. 그전까지 라벨 필터는 0건을 낸다.

### 테스트 함정 기록

nori는 "보고서"를 색인과 질의에서 다르게 분해해, 제목에 그 낱말이 그대로 있어도 검색에
걸리지 않았다. 검색 테스트의 낱말은 **실제로 매칭되는 것**으로 골라야 한다 — 아니면 필터가
아니라 검색어 때문에 0건이 나오고, 원인을 필터에서 찾게 된다(이번에 실제로 그랬다).

## 10. W23 — 인라인 댓글 UX 재작업 (2026-08-30)

이전에는 인라인 스레드를 본문 아래에 목록으로 통째로 펼쳐 놨다. 인용문이 본문과 떨어져 있어
"어느 문장 얘기인지"가 매번 사라졌고, 대화가 아니라 메모 더미로 읽혔다.

컨플루언스 방식으로 바꿨다. 본문에는 **댓글이 달렸다는 것만** 보인다 — 배경색 + 밑줄, 그리고
구간 끝의 말풍선(답글 수 포함). 밑줄을 함께 쓰는 이유는 배경색만으로는 검색 하이라이트·인용과
구분되지 않기 때문이다.

| 동작 | 방식 |
|---|---|
| 대화 열기 | 하이라이트 클릭(키보드는 Enter·Space) → 그 줄 오른쪽 상자 |
| 대화 잇기 | 상자 안에서 답글 — 페이지 댓글과 같은 1단 중첩 규칙 |
| 새로 달기 | 본문을 골라 **우클릭** → "댓글 달기" → 같은 상자에서 작성 |
| 해결 | 상자에서 해결 → 하이라이트가 내려가고 "해결된 대화"로 접힌다 |

고른 구간이 없는 우클릭은 브라우저 기본 메뉴를 그대로 둔다 — 댓글과 무관한 우클릭까지 뺏으면
링크 복사 같은 일상 동작이 막힌다.

상자는 1280px 이상에서만 오른쪽 레일로 띄운다. 본문이 760px 중앙 정렬이라 그보다 좁으면
레일을 우겨넣어도 본문을 덮는다 — 좁은 화면에서는 그 줄 바로 아래에 편다.

**전체 너비**에서는 본문이 화면을 다 써서 레일 자리가 없다. 밖으로 밀면 페이지를 넘어가므로
오른쪽 끝 **안쪽**에 붙이고, 댓글 단 줄을 가리지 않게 그 줄 아래에 편다.

하이라이트가 유일한 진입점이 됐으므로, 본문에서 사라지는 대화만 아래 목록에 남긴다: 편집으로
인용 구간을 못 찾게 된 스레드와 해결된 스레드. 둘 다 하이라이트가 없어 안 남기면 영영 닿을 수
없다.

### 테스트가 놓치고 있던 것

기존 화면 테스트는 본문에 **없는** 낱말("온보딩")을 앵커로 잡고 있었다. 스레드 목록이 위치를
못 찾아도 그냥 그려졌기 때문에 그린이었다 — 하이라이트가 실제로 붙는지는 아무도 검증하지
않았다. 본문에 있는 낱말로 바꾸고, 하이라이트를 눌러야 대화가 보이는 것으로 계약을 세웠다.

## 11. W23 — 글로벌 네비 최근·스페이스 플라이아웃 (2026-08-30)

"최근"은 비활성 자리표시였고 "스페이스"는 곧장 목록 화면으로 튀었다. 별표 표시만 플라이아웃을
갖고 있어 세 항목의 형태가 제각각이었다.

셋 다 화살표 + 오른쪽 상자로 통일했다. 다만 내용의 성격이 달라 상자 안은 두 갈래다:

- **별표 표시**(기존): 검색형. 사용자가 스스로 모은 것이라 수가 많고, 이름을 알고 찾는다.
- **최근·스페이스**(신규 `NavListFlyout`): 목록형. 최신순·이름순으로 훑는다. 상위 10개만
  보여주고 하단 "전체 보기"로 목록 화면(`/home`, `/spaces`)에 넘긴다.

최근 방문 로그는 페이지 id만 저장한다. 사이드바가 항상 들고 있을 이유가 없어 **상자를 열 때**
하이드레이트하고, 지워진 페이지는 떨어뜨린다 — 방문 로그가 죽은 링크를 남기지 않는다.

## 12. 검색 계약 구멍 (2026-08-30)

프론트는 결과 목록에서 폴더와 문서를 다른 아이콘으로 그리려고 `pageType`을 물어보는데, 검색
계약에 그 필드가 없었다. GraphQL은 모르는 필드를 만나면 **질의 전체**를 검증 오류로 떨어뜨리므로
실서버 모드의 검색 화면이 통째로 에러 배너였다. 색인에는 이미 `type`이 있었고 계약에만 없었다.

통합 테스트가 프론트보다 적은 필드를 물어봐서 이 구멍이 오래 그린으로 통과했다. 질의를 프론트와
같은 필드 목록으로 맞추고 이유를 주석에 남겼다 — 계약 테스트가 클라이언트보다 적게 물어보면
계약을 지키는 게 아니다.

## 13. 변경 요약 칸이 에디터를 덮던 문제 (2026-08-30)

액션 바(`.edit-chrome`)는 높이가 `--edit-chrome-height`(52px)로 선언돼 있고, 바로 아래 툴바가
그 값만큼 sticky top을 내려 두 바가 겹치지 않게 맞춰져 있다. 변경 요약 입력에 라벨이 붙으면서
바가 그 높이를 넘겼고, 툴바는 여전히 52px에서 멈춰 스크롤하는 순간 바가 툴바와 본문을 덮었다.

라벨을 화면에서만 감췄다(접근성 트리에는 남는다 — `getByLabelText`로 여전히 찾을 수 있다).
무엇을 적는 칸인지는 placeholder가 말한다.

이 종류의 desync는 CSS 변수 하나가 실제 높이와 어긋나는 순간 조용히 생긴다. 액션 바에 세로로
쌓이는 컨트롤을 넣을 때는 `--edit-chrome-height`를 함께 확인한다.

## 14. 라이트 검색 — OpenSearch를 옵션으로 (2026-08-30)

온프렘 설치에 따라 OpenSearch를 띄울지 고를 수 있어야 한다는 요구. 실측 회수 메모리는
**opensearch 1.3GiB + search-service 436MiB = 약 1.75GB**다. 컨테이너 14개가 한 머신에서 도는
소규모 설치에서는 뺄 이유가 충분하다.

### 이미 되어 있던 것

- 게이트웨이의 search 라우트가 `SEARCH_SERVICE_URI` 환경변수로 목적지를 갈아끼운다.
- 라우트 단위 5xx 격리 — "search-service가 죽어도 코어는 무영향"이 설계에 이미 있다.
- 사이드바 페이지 검색과 `[[` 자동완성은 애초에 OpenSearch를 안 쓴다(wiki-backend의 제목 검색).
- Redis 스트림은 `MAXLEN ~100000`으로 자가 트림 — 소비자가 없어도 무한히 쌓이지 않는다.

### 넣은 것

wiki-backend가 **같은 GraphQL 계약**을 Postgres로 구현한다(`search.graphqls`, `LiteSearchService`).
스위치는 게이트웨이의 `SEARCH_SERVICE_URI` **하나뿐**이다 — 두 곳에 두면 반쪽만 바뀐 배포가 생긴다.
프론트는 무수정이다.

| 항목 | OpenSearch 배포 | 라이트 배포 |
|---|---|---|
| 매칭 | nori 형태소 분석 | `lower(col) like '%q%'` 부분 문자열 |
| 인덱스 | 역색인 | pg_trgm GIN(V18) |
| 대상 | 위키 + 앞으로 합류할 도메인 | 위키(페이지·첨부)만 |
| 하이라이트 | highlighter | 검색어 주변 잘라내기 |
| 재색인 | `/admin/reindex` | 없음(색인이 없다) |

부분 문자열이 형태소 분석보다 나은 구석도 있다. Postgres 기본 tsvector(`simple`)는 한국어가
교착어라 "설정을"이 "설정"에 걸리지 않는데 부분 문자열은 걸린다.

### 권한

스페이스 단위는 SQL의 `in` 절로, 페이지 단위 제한(W18)은 가져온 뒤 후필터로 거른다 — SQL로
판정할 수 없기 때문이다. OpenSearch 경로도 같은 구조다(`filterVisiblePages` gRPC).

후필터가 도는 후보 창은 500건으로 묶었다. 창을 채웠으면 `total`은 "적어도 이만큼"이므로
`totalExact=false`로 사실대로 알린다 — 계약에 이미 있던 필드가 정확히 이 용도다.

### 한계 (명시적 전제)

문서가 수만 건을 넘어가면 `like '%q%'`는 trgm 인덱스로도 느려진다. 라이트 검색은 **소규모
설치용**이고, 그 규모를 넘으면 `SEARCH_SERVICE_URI`를 되돌려 OpenSearch 배포로 옮긴다.

### 벡터 검색 / RAG

엔진을 바꿀 필요는 없다 — OpenSearch는 `knn_vector`를 내장해서 임베딩 필드를 매핑에 추가하고
하이브리드 질의(BM25 + kNN)로 확장하면 된다. 라이트 티어에도 AI가 필요해지면 Postgres에
`pgvector`를 얹는 길이 따로 있다. 다만 축을 둘로 쪼개면 조합이 넷이 되고 넷 다 테스트해야
하므로, 처음에는 **티어 하나**로 묶는다: 라이트는 AI 없음, 풀은 AI 가능.

## 15. W23 — 검색 마무리 (2026-08-30)

세 기능 모두 **OpenSearch 없이도 동작해야 한다**는 것이 전제였다. 그 제약이 설계를 정했다.

### 정렬

`RELEVANCE`(기본)·`UPDATED_DESC`·`UPDATED_ASC`. 두 엔진이 같은 값으로 같은 순서를 낸다 —
배포에 따라 "최신순"이 다르면 사용자는 어느 쪽이 맞는지 알 수 없다.

동점은 **정렬 방향을 따라** id로 가른다. 최신순에서 같은 시각이면 나중에 만들어진 쪽(큰 id)이
위여야 말과 어긋나지 않는다. 기준이 흔들리면 2페이지에서 1페이지 항목이 다시 보인다.

관련도에는 OpenSearch 쪽에 정렬 절을 붙이지 않았다. 기본이 `_score`라, 명시하면 동점 처리까지
우리가 떠안는다.

### 결과 경로

`GET /api/wiki/pages/paths?id=..` — 루트부터 부모까지, 자기 자신은 뺀다(제목은 이미 크게 보인다).

**색인이 아니라 별도 조회로 뒀다.** 색인에 경로를 넣으면 (1) 문서를 옮길 때마다 그 하위 전체를
재색인해야 하고 (2) 라이트 배포에는 그 경로가 아예 없다. 검색 엔진을 타지 않는 조회로 두면 두
배포가 같은 답을 낸다. 비용은 결과 한 페이지당 요청 하나이고 상한이 20건이다.

볼 수 없는 문서는 답에서 뺀다 — 경로만 흘려도 제한된 문서의 위치와 제목이 샌다.

기존에는 이 자리에 `스페이스명 / 스페이스키`가 있었는데, 이름 옆의 키는 같은 말을 두 번 하는
것이라 "어디에 있는 문서인가"를 알려주지 못했다.

### 라벨 자동완성

`GET /api/wiki/labels?q=` — 접근 가능한 스페이스 전체에서 **접두** 일치, 건수 많은 순, 20개.

라벨 필터를 붙이면서 만든 부채를 갚은 것이다. 전역 라벨 목록 API가 없어 자유 텍스트로 뒀는데,
오타를 치면 0건이 나오고 사용자는 이유를 알 수 없었다.

접두 일치인 이유: 라벨은 짧고 사용자가 앞에서부터 친다. 부분 일치로 열면 인덱스를 못 타는 데다
"설계"를 치면 "재설계"까지 올라와 고르기가 어려워진다. 화면은 `datalist`라 후보에 없는 라벨을
직접 입력하는 길도 막지 않는다.

### 테스트에서 걸러낸 것

정렬 테스트가 저장 시각에 기대고 있어 간헐 실패했다 — 연달아 저장하면 같은 시각이 찍혀 순서가
tie-break에 달린다. 시각을 못 박아 없앴고, 그 과정에서 tie-break 방향 버그도 같이 드러났다.

## 16. W23 — 콘텐츠 생산성 (2026-08-30)

### 하위 포함 복제

`POST /api/wiki/pages/{id}/copy`에 본문을 붙인다(생략하면 기존 단일 페이지 복사 그대로).

사본 표시(`(사본)`)는 **뿌리에만** 붙인다. 하위까지 제목을 바꾸면 문서 안의 `[[제목]]`이 전부
어긋난다 — 이 위키의 내부 링크는 제목으로 해석되기 때문이다.

**볼 수 없는 하위는 사본에 넣지 않는다.** 사용자는 애초에 그 문서의 존재를 모르며, 몰래 복사해
열어 두는 쪽이 훨씬 나쁘다. VIEW 제한은 하위로 상속되므로 가려진 노드를 빼면 그 아래도 자연히
빠진다.

**제한은 기본으로 함께 복사한다**(`includeRestrictions` 생략 시 true). 제한된 문서를 복사했는데
사본이 열려 있으면 복사 한 번으로 스페이스 전체에 내용이 열린다 — 그 사고가 "사본에 제한이 남아
불편하다"보다 훨씬 나쁘다. 열려면 명시적으로 끈다. 기존 단일 복사의 동작이 바뀌는 지점이다.

한 번에 200개까지다. 페이지마다 첨부를 저장소에서 읽어 다시 쓰므로 한 트랜잭션에서 무한정 돌릴
일이 아니고, 넘으면 거절해서 절반만 복사된 트리를 남기지 않는다.

### 페이지 템플릿

스페이스 스코프 CRUD(V19) + "이 페이지를 템플릿으로 저장".

| 결정 | 이유 |
|---|---|
| 읽기 VIEW / 쓰기 **ADMIN** | 그 스페이스 모두가 새 문서를 만들 때 마주치는 공용 자산이다. 편집 권한자 아무나 바꾸면 팀의 문서 형식이 조용히 흔들린다 |
| 본문은 마크다운 문자열 | 저장 포맷은 하나다. 별도 표현을 두면 템플릿에서 만든 문서와 직접 쓴 문서가 갈린다 |
| 스페이스 스코프만 | 전역 목록은 관리 주체가 모호해진다. 필요해지면 `space_id`를 nullable로 여는 마이그레이션을 더한다 |
| 페이지→템플릿은 **본문만** | 제목까지 가져오면 그 템플릿으로 만든 문서마다 같은 제목이 붙는다. 첨부는 그 문서에 딸린 것이지 형식이 아니다 |
| 목록에서도 본문을 준다 | 템플릿은 짧고, 미리보기가 곧 선택 근거다 |
| 이름 정규화(연속 공백 축약) | 앞뒤·연속 공백만 다른 이름은 고르는 화면에서 구분되지 않는다 |

템플릿 편집은 마크다운 원문으로 한다. 리치 에디터를 붙이면 편집기 스키마와 템플릿 저장 형식이
갈라질 위험이 생기는데, 템플릿은 대개 머리말과 빈 섹션 몇 줄이라 그럴 값어치가 없다.

**남은 것:** 컨플루언스 블루프린트의 "생성 시 입력 폼"(변수 치환)은 없다. 지금은 본문을 그대로
복사해 초안을 만든다.

## 17. W23 — 스페이스 설정 전용 화면 (2026-08-30)

설정을 탭으로 두니 항목이 늘어날수록 가로로 밀렸고(일반·권한·템플릿·삭제로 이미 넷), 어느
설정을 보고 있는지가 URL에 남지 않아 공유도 뒤로가기도 성립하지 않았다.

**전용 사이드바를 가진 별도 화면**으로 바꿨다. 설정은 페이지 트리와 함께 볼 이유가 없다 —
컨플루언스 스페이스 설정과 같은 구조다.

| 바뀐 것 | 내용 |
|---|---|
| 경로 | `/spaces/:id/settings/:section` (`general`·`permissions`·`templates`·`danger`) |
| 사이드바 | 설정 화면에서는 페이지 트리 대신 설정 내비게이션으로 통째로 바뀐다 |
| 진입점 | 스페이스 이름에 마우스를 올리면 나타나는 **"…"** 메뉴 |

이름 버튼 자체는 스페이스 전환이라 설정을 같은 버튼에 얹을 수 없었다. "…"은 hover에서만
보이되 **키보드 포커스에는 반드시 나타난다** — 보이지 않는 버튼에는 도달할 수 없다.

사이드바 하단에 있던 "스페이스 설정" 링크는 없앴다. 진입점이 둘이면 어디가 정본인지 알 수
없다. 라벨·휴지통은 자주 쓰는 탐색이라 사이드바에 남기고 "…" 메뉴에도 함께 넣었다.

설정 사이드바 맨 위의 "돌아가기"가 유일한 탈출구다 — 트리가 없어서 이게 없으면 브라우저
뒤로가기밖에 남지 않는다.

## 18. W23 — 첨부 버전과 PDF 미리보기 (2026-08-30)

### 같은 이름 재업로드가 새 버전이 된다

전에는 같은 이름의 파일을 다시 올리면 **새 행이 생겨 id가 바뀌었다.** 본문의 인라인 참조는
첨부 id로 걸려 있으므로, 이미지를 고쳐 올려도 문서에는 옛 파일이 계속 보였다. 사용자가 할 수
있는 일이라고는 본문의 참조를 손으로 갈아끼우는 것뿐이었다.

이제 같은 페이지·같은 이름·확정 상태의 첨부가 있으면 **그 행을 갈아끼우고**(V20) 직전 내용을
`attachment_version`에 쌓는다. id가 유지되니 문서 어디에 박혀 있든 새 파일이 나온다 — 이 id
유지가 기능의 요점이라 테스트도 거기에 걸었다.

| 결정 | 이유 |
|---|---|
| PENDING 업로드는 대상 아님 | 편집 중 임시 파일이라 갈아끼울 "현재"가 없고, 편집을 취소하면 사라져야 한다 |
| 되돌리기도 새 버전으로 쌓음 | 되돌린 사실이 이력에 남고, 같은 저장 객체를 두 행이 가리켜 한쪽을 지울 때 깨지는 일이 없다 |
| 되돌릴 때 파일을 복사하지 않음 | 같은 바이트다. 좌표만 현재로 올린다 |
| 지난 버전은 내려받기만 | 옛 파일을 문서에 다시 심을 이유가 없다 — 그건 되돌리기다 |

**행 삭제를 DB의 FK CASCADE에 맡기지 않는다.** JPA 매핑에 관계가 없어(컬럼만 들고 있다)
스키마를 Hibernate가 만드는 환경에는 그 제약이 아예 없다 — 테스트에서 실제로 그렇게 드러났다.
파일도 어차피 코드에서 지워야 하므로 행도 같은 자리에서 지운다.

### PDF 미리보기

`/inline`의 허용 목록에 `application/pdf`를 더했다. 브라우저 내장 뷰어가 자체 샌드박스에서
열고 DOM에 닿지 못하며, 첨부 미리보기가 필요한 문서의 대부분이 PDF다. 응답에는 `nosniff`와
same-origin CORP를 함께 건다.

**SVG·HTML은 넣지 않는다.** 브라우저가 문서로 실행해서 스크립트가 우리 오리진에서 돌기
때문이다. 허용 목록에 없는 타입은 415로 거절한다(테스트로 고정).

갭 문서의 "항상 `Content-Disposition: attachment`"는 낡은 기록이었다 — `/inline`은 W21-3부터
있었고 래스터 이미지만 열려 있었다.

## 19. W23 — 별표·최근 방문의 서버 이전 (2026-08-30)

둘 다 브라우저 localStorage에만 있었다. 회사 노트북에서 별표한 문서가 집 컴퓨터에는 없고,
브라우저 데이터를 한 번 지우면 그동안 모아 둔 즐겨찾기가 통째로 사라졌다. "이 사용자가 무엇을
아껴 보는가"는 사이드바 폭 같은 UI 프리퍼런스가 아니라 사용자 데이터다.

### 서버가 원장, 브라우저는 사본

localStorage를 없애지 않았다. 화면은 계속 사본을 즉시 읽어 그리고(첫 렌더에 네트워크를 기다리지
않는다), 앱이 뜰 때 한 번 동기화가 사본을 원장으로 덮는다. 토글은 사본을 먼저 바꾸고 서버로
보낸다 — 별 하나 누르는 데 왕복을 기다릴 이유가 없다.

실패해도 사본을 되돌리지 않는다. 다음 동기화가 바로잡고, 그전까지는 사용자가 방금 누른 대로
보이는 쪽이 덜 혼란스럽다.

### 잃지 않게 하는 두 가지 장치

- **1회 이관**: 서버가 비었는데 사본에만 별표가 있으면 한 번 올려 보낸다. 이 기능이 생기기
  전에 모아 둔 것을 잃지 않기 위해서다.
- **이관 표시**: 한 번 올렸으면 표시를 남긴다. 없으면 사용자가 스스로 전부 지운 뒤 다음 실행에서
  옛 별표가 되살아난다.
- **null ≠ 빈 목록**: 목업 모드의 `listStars()`는 null을 준다("서버 원장이 없다"). 빈 목록으로
  덮으면 목업에서 별표가 날아간다. 이 구분이 이 모듈의 핵심 위험이라 테스트도 거기에 몰려 있다.

### 읽을 때마다 다시 거른다

별표해 둔 뒤 권한이 회수될 수 있다. 그때 목록에 제목이 남아 있으면 그것만으로 정보가 샌다 —
스페이스 권한(org)과 페이지 단위 제한(W18)을 **읽을 때마다** 다시 적용한다.

반대로 **별표 해제는 볼 수 없게 된 문서에도 통한다.** 아니면 목록에서 뺄 방법이 없다.

### 방문 기록

`POST /pages/{id}/views`(조회수 증가)가 이미 모든 열람에서 도므로 거기서 함께 남긴다 — 왕복을
늘릴 이유가 없다. 사용자·페이지당 한 줄이고 다시 보면 시각만 갱신한다. 방문마다 줄을 쌓지 않는
이유는 필요한 것이 "마지막으로 언제 봤나"뿐이고, 매 방문을 남기면 활동 이력이 되어 보존 정책이
따라붙기 때문이다. 20건을 넘으면 오래된 것부터 버린다.

## 20. W23 — 검색 색인 관리 화면 (2026-08-30)

색인 매핑이 `dynamic: strict`라 새 필드를 더한 배포 뒤에는 **재색인해야 그 필드가 채워진다.**
그전까지 새 필터는 오류 없이 0건만 낸다 — 라벨 필터가 실제로 그렇게 조용히 죽어 있었다.

그런데 재색인은 전역 관리자 토큰이 필요한 REST 하나뿐이었고, 그 토큰은 설계상 브라우저 메모리
에만 있다(AT는 메모리, RT는 HttpOnly 쿠키). 즉 개발자도구 네트워크 탭에서 요청을 복사해 손으로
호출하는 것 말고는 방법이 없었다. 색인 필드는 앞으로도 늘어나므로 그 수작업을 화면으로 옮긴다.

- 상단 설정 드롭다운 → **검색 색인 관리** (`/admin/search`)
- 지금 서비스 중인 세대(`wiki-page-v5` 같은)와 문서 수를 보여준다 — 재색인이 필요한지 눈으로
  판단할 근거다
- 재색인 시작 + 진행 중인 잡 따라가기(2초 간격, **진행 중일 때만**)

### 관리자 여부를 무엇으로 판단하는가

org-service의 **GLOBAL ADMIN grant**다. 토큰의 `roles` 클레임은 Keycloak realm role이라 다른
개념이고, 둘은 얼마든지 어긋날 수 있다. 그래서 권위 있는 곳에 직접 물어본다 — 현황 조회
(`GET /admin/reindex/status`)가 통하면 관리자다. 상단바는 앱당 한 번 마운트되므로 세션당 요청
하나로 끝난다.

관리자가 아니면 메뉴 항목 자체가 없다. 띄워 놓고 눌렀을 때 "권한 없음"을 보여주는 것보다 낫다.
직접 URL로 들어오면 화면이 스스로 그 사실을 알린다.

화면에 "왜 눌러야 하는가"를 적어 뒀다. 자주 쓰지 않는 버튼이라, 정작 필요한 순간에 "이게
뭐였더라"가 되면 또 개발자도구를 열게 된다.

## 21. W23 — 감사 로그 (2026-08-30)

"누가 이 문서를 지웠나", "언제부터 이 페이지가 잠겼나"를 확인할 방법이 없었다. 이력이 남는
것은 본문 리비전뿐이고, 지우기·제한 변경처럼 되돌리기 어려운 조작은 흔적이 없었다.

스페이스 설정에 **감사 로그** 섹션을 넣었다(V22, 스페이스 ADMIN만).

### 무엇을 남기는가

| 남긴다 | 남기지 않는다 |
|---|---|
| 휴지통 이동·복원·영구 삭제 | **본문 수정** — 리비전이 이미 남긴다 |
| 문서 제한(W18) 변경 | 조회 — 남기면 감사가 아니라 활동 추적이 되어 보존 정책이 따라붙는다 |
| 첨부 삭제 | |
| 스페이스 정보 변경 | |
| 템플릿 추가·수정·삭제 | |

되돌리기 어렵거나 접근 범위를 바꾸는 것만이 기준이다. 전부 남기면 정작 볼 것이 묻힌다.

### 대상 이름을 함께 저장한다

id만 남기면 지워진 문서의 기록이 숫자만 남아 아무도 못 알아본다 — 그리고 그 행은 이미 없어서
조회할 수도 없다. 기록 시점의 이름을 스냅샷으로 박아 둔다. 그래서 **지우기 전에** 기록한다.

### 조회는 ADMIN만

누가 무엇을 지웠는지는 그 스페이스를 볼 수 있는 모두가 알아야 할 정보가 아니다. 제한된 문서의
제목이 기록에 남아 있기도 하다.

### 스페이스 삭제는 기록하지 않는다

기록이 스페이스 스코프라 삭제와 함께 사라진다 — 남겨도 읽을 곳이 없다. 전역 감사 로그가
생겨야 담을 수 있다.

### 순환 참조에서 배운 것

처음에 `AuditService`가 권한 판정을 `SpaceService`에 위임했더니 순환이 됐다: 기록을 남기는
쪽(`SpaceService`·`PageService`·`AttachmentService`)이 전부 `AuditService`를 부르기 때문이다.
감사 서비스는 **기록기이지 상위 서비스가 아니다** — 판정에 필요한 최소한(`PermissionClient`)만
직접 들고 있게 바꿨다.

### 나머지 절반 — 권한 변경 (같은 날 이어서)

**스페이스 grant 변경은 org-service가 소유**하고 프론트가 `/api/org/grants`로 직접 부른다.
wiki-backend는 그 조작을 보지 못한다 — 감사에서 가장 궁금한 것이 "누가 이 사람에게 권한을
줬나"인데 정작 그게 빠져 있었다.

org-service에 `grant_audit`(V2)과 `GET /api/org/grants/audit`을 넣고, 화면이 두 목록을 시각순
으로 합친다.

**응답 필드를 wiki-backend의 감사 항목과 같은 모양으로 맞췄다.** 다른 모양으로 주면 합치는
쪽에 변환 코드가 생기고, 그 변환이 곧 어긋난다.

권한 이력을 못 읽는다고 위키 기록까지 감추지는 않는다 — 조회 범위가 서로 다를 수 있고, 그때
화면이 통째로 비면 있는 기록도 못 보게 된다.

여기서도 대상 이름을 함께 저장한다. 사용자가 지워지거나 팀이 사라져도 기록은 읽혀야 한다.
이름을 못 찾으면 id로 대신한다 — 이름을 못 읽는다고 권한 조작을 실패시킬 이유는 없다.

## 22. W23 — 리액션 (2026-08-30)

"잘 봤다"를 표현할 방법이 댓글뿐이었다. 한마디 남기자고 댓글을 쓰면 스레드가 잡음으로 차고,
그래서 아무도 안 남긴다 — 문서가 읽히는지 작성자가 알 길이 없었다.

문서 본문 아래와 댓글마다 리액션 줄을 붙였다(V23).

| 결정 | 이유 |
|---|---|
| 이모지 **고정 6종** | 아무 문자나 받으면 집계가 예측 불가능한 기호로 차고, 유니코드 정규화 차이로 같은 이모지가 두 줄이 된다 |
| 문서·댓글이 한 표(`target_type`) | 나누면 집계·토글 코드가 두 벌이 된다 |
| 키 = (대상, 사용자, 이모지) | 같은 이모지를 두 번 누를 수 없다 — 토글이 곧 이 제약이고, 재시도가 수를 부풀리지 않는다 |
| 응답은 집계만 | "누가 눌렀나" 목록을 열면 "누가 안 눌렀나"까지 읽히는 화면이 된다 |
| 칩 순서 = 집합 순서 | 수가 바뀔 때마다 칩이 자리를 옮기면 누르려던 것을 놓친다 |
| 댓글 목록이 리액션을 함께 준다 | 댓글마다 따로 물으면 N+1 |

볼 수 있으면 누를 수 있다 — 댓글과 같은 기준선이다. 제한된 문서에는 누를 수 없다(존재 여부가
새지 않아야 한다).

화면은 낙관적으로 그린 뒤 서버 응답의 집계로 덮는다 — 그사이 다른 사람이 누른 수가 그때
맞춰진다. 실패하면 이전 값으로 되돌린다.

리액션은 FK 없이 `(type, id)`로만 매달려 있어 댓글·문서를 지울 때 코드에서 함께 걷어낸다 —
남으면 다음 id가 그 수를 물려받을 수 있다.

## 23. W23 — 페이지 공유 (2026-08-30)

"이 문서 봐주세요"를 전할 방법이 없었다. 링크를 메신저에 붙이거나 본문에 멘션을 억지로 넣어야
했다 — 후자는 문서를 더럽힌다.

페이지 헤더에 **공유** 버튼. 받는 사람을 고르고 메모를 붙이면 수신자 알림함에 뜬다(V24).

| 결정 | 이유 |
|---|---|
| 알림의 한 종류(`SHARED`) | 수신자 입장에서는 "누가 나를 이 문서로 불렀다"이고, 그것이 알림함이 하는 일이다. 별도 표를 두면 읽음·목록·권한 필터를 두 벌 만든다 |
| 합치지 않음 | 두 사람이 같은 문서를 각자 다른 메모로 보냈으면 둘 다 의미 있다(멘션과 같은 규칙) |
| 공유해도 권한은 안 생김 | 권한은 org-service 원장이고 공유는 알림이다. 볼 수 없는 수신자는 조용히 빠지고 **전달 수**로 드러난다 |
| 자신은 건너뜀 | 자신에게 보내는 공유는 의미가 없다 |
| 링크 복사도 여기 | 공유의 절반은 URL을 어디에 붙이는 것인데 그 버튼이 트리 "…"에만 있었다 |

이메일 채널은 넣지 않았다 — 발송 인프라(SMTP·템플릿·수신 거부)가 없고, 알림 이메일 채널
항목과 함께 결정해야 한다.

## 24. W23 — 페이지 보관 (2026-08-30)

휴지통은 "지웠다"이고 보관은 "끝났지만 남겨 둔다"다. 지난 분기 회고·폐기된 설계처럼 더는 트리에
있을 이유가 없지만 링크로는 계속 읽혀야 하는 문서가 트리를 채우고 있었다 — 트리는 갈수록 읽기
어려워지고, 지우자니 링크가 끊긴다.

| 결정 | 이유 |
|---|---|
| `@SQLRestriction`에 걸지 않음(V25) | 보관은 숨김이지 삭제가 아니다. 직접 링크로 열려야 하므로 조회에서 빠지면 안 되고, 트리·검색·자동완성 쿼리에서만 `archived_at is null`로 뺀다 |
| 휴지통과 같은 묶음 규칙 | 루트 표시 + 하위 cascade, 따로 보관한 하위 묶음은 경계. 목록 행(`TrashItem`)과 읽는 코드를 공유한다 |
| 보관 중 편집 불가(409) | "끝났다"는 뜻이다. 고치려면 먼저 해제 — 그 사실을 본문 위 배너로 알린다 |
| 상위가 보관 중이면 하위만 해제 불가 | 트리에 나타날 자리가 없다 |
| 검색 색인에서 뺌 | 보관 시 `pageDeleted` 이벤트, 해제 시 `pageUpdated`. 라이트 검색은 쿼리에서 뺀다 |
| 권한은 EDIT | 트리에서 문서를 치우는 것은 편집과 같은 무게다 |

자리는 그대로다 — 보관은 이동이 아니라 parent·순번을 건드리지 않고, 해제하면 원래 자리로
돌아온다(휴지통 복원과 달리 부모가 사라질 일이 없다. 부모가 보관 중이면 해제를 막는다).

## 25. W23 — 섹션 앵커 (2026-08-30)

rehype-slug가 헤딩 id를 이미 붙여 두고 있었는데 그 id를 복사할 방법이 없어서, 문서의 한 절을
가리키려면 주소창에서 손으로 `#`을 붙여야 했다.

- 헤딩에 마우스를 올리면 끝에 링크 버튼이 나타난다(키보드 포커스에도). 누르면 `…#slug` 복사
- `#slug`로 들어오면 본문이 그려진 **뒤** 그 절로 내린다 — 본문이 비동기라 브라우저 기본 앵커
  점프는 대상이 없을 때 일어나 빈손으로 끝난다

**버튼에 글자를 두지 않는다.** 인라인 댓글 앵커가 렌더된 본문의 텍스트로 구간을 잡으므로 "#"
같은 글자가 헤딩에 섞이면 인용 매칭이 어긋난다. 토스트도 쓰지 않는다 — 이 렌더러는 미리보기·
내보내기 등 Provider 밖에서도 그려진다. 복사 결과는 버튼이 잠깐 "복사됨"으로 바뀌어 알린다.

## 26. W23 — 발췌·발췌 포함 (2026-08-30)

컨플루언스 Excerpt / Excerpt Include. 한 문서의 요약을 여러 문서에 복사해 두면 하나를 고칠 때
나머지가 낡는다 — 원본에서 "가져다 써도 되는 부분"을 표시하고 다른 문서가 그것을 끌어온다.

| 저장 | 의미 |
|---|---|
| `:::excerpt` … `:::` | 원본 문서의 발췌 블록. 보기 화면에서 띠와 "발췌" 꼬리표로 표시 |
| `::excerpt-include[제목]` | 같은 스페이스의 그 문서에서 발췌를 가져와 이 자리에 그린다 |

둘 다 remark-directive 문법 가족(`:::columns`·`::toc`)이라 새 개념을 들이지 않고, 저장 포맷은
계속 마크다운 문자열이다. 편집기는 이 지시자를 모르므로 마커 텍스트로 보인다(목차·패널과 같은
방식). 편집기가 여는 콜론을 `\:`로 이스케이프할 수 있어 보기 경로 진입 전에 되돌린다 — **줄
전체가 지시자인 경우에만** 풀어 본문의 리터럴 `\:`를 건드리지 않는다.

| 결정 | 이유 |
|---|---|
| 제목으로 찾는다 | 내부 링크(`[[제목]]`)가 제목으로 해석되므로 같은 규칙 |
| 발췌 블록이 없으면 첫 문단으로 대신하지 않음 | 작성자가 "가져다 써도 되는 부분"을 정하지 않은 문서다. 그 사실을 알리고 링크만 준다 |
| 한 단계만 따라감 | 발췌 안의 `::excerpt-include`는 마커로 남긴다 — 서로를 포함하는 두 문서가 무한히 펼쳐지는 것을 막는다 |
| 깨진 포함은 경고 색 | 조용히 비어 있으면 왜 안 나오는지 모른다 |

## 27. W23 — 액션 아이템 (2026-08-30)

체크박스 목록은 있었지만 "누가 언제까지"가 없어서 회의록의 할 일이 회의록 안에서만 살았다 —
내 몫이 어느 문서에 흩어져 있는지 볼 방법이 없었다.

**새 문법을 들이지 않았다.** 항목 안의 멘션이 담당자, 날짜 요소가 기한이다:

```
- [ ] 배포 공지 [@김철수](user:12) [2026-09-01](date:2026-09-01)
```

| 결정 | 이유 |
|---|---|
| 본문의 파생 표(`page_task`, V26) | 백링크·라벨과 같은 계열. 저장할 때마다 통째로 다시 만든다 — 줄이 밀리면 줄 번호로 찾는 토글이 엉뚱한 줄을 건드리므로 표가 항상 현재 본문과 같아야 한다 |
| 토글 = 편집 | 본문의 그 줄을 다시 쓴다. 버전·리비전("작업 완료 표시")·EDIT 권한이 전부 따라간다. 목록과 문서가 따로 놀지 않는다 |
| 줄이 이미 다른 내용이면 409 | 동시 편집으로 밀린 줄을 건드리지 않는다 |
| 내 작업은 읽을 때마다 권한으로 거른다 | 문서가 잠긴 뒤에도 항목 텍스트가 남으면 그것만으로 샌다(별표와 같은 이유) |
| 정렬 | 기한 있는 것이 먼저(임박한 순), 없는 것은 뒤. 지난 기한은 붉게 |

본문 체크박스도 살렸다. remark-gfm은 `disabled`로 그리는데, hast 노드의 `position`에서 줄 번호를
얻어 그 줄을 토글한다 — 정규화·링크 해석은 줄 수를 바꾸지 않으므로 번호가 서버와 같다.
미리보기·발췌·내보내기 렌더는 핸들러가 없어 이전처럼 읽기 전용이다.

## 28. W23 — 개인 스페이스 (2026-08-30)

팀 스페이스에 넣기 애매한 메모·초안을 둘 곳이 없어서 사람들이 팀 스페이스 한구석에 "OO 작업
메모" 폴더를 만들었다 — 남의 트리를 어지럽히고, 본인은 그것이 어디 있는지 매번 찾는다.

| 결정 | 이유 |
|---|---|
| 별도 표가 아니라 `space.owner_id`(V27) | 개인 스페이스도 스페이스다 — 권한·트리·검색·보관·휴지통이 전부 같다. 다른 점은 "누구의 것인가"뿐 |
| 한 사람에 하나(부분 유니크) | 두 개면 "내 스페이스"가 어느 것인지 물어야 한다 |
| key는 서버가 정한다(`me-{id}`) | 사용자 입력 key(`[a-z0-9-]`)와 겹치지 않는 접두 |
| 글로벌 네비 "내 스페이스" — 없으면 그 자리에서 생성 | 이름·키가 정해져 있어 물어볼 것이 없다. "만들기" 단계는 마찰일 뿐 |
| 주인 ADMIN 부여가 실패하면 되돌림 | 일반 생성은 grants REST로 수습 가능하지만, 개인 스페이스는 "내 것"이 전제라 주인이 못 들어가는 상태를 남기지 않는다 |

남의 개인 스페이스는 일반 권한 규칙대로 보이지 않는다(전역 관리자 제외). 공유하고 싶으면
스페이스 설정 → 권한에서 사람을 더하면 된다 — 팀 스페이스와 같은 길이다.

## 29. W23 — 팀 관리 화면 (2026-08-30)

스페이스 권한 부여에는 팀을 쓸 수 있었는데(W22) 정작 팀을 만들 화면이 없었다 — org-service
REST를 curl로 때려야 했다.

- org-service에 `GET /api/org/teams/{id}/members`를 더했다(이름을 함께 준다 — 화면이 멤버
  디렉터리를 다시 뒤지지 않는다). 나머지 쓰기 API는 이미 있었다
- 상단 설정 → **팀 관리**(`/admin/teams`). 메뉴 항목은 검색 색인 관리와 같은 게이트(전역
  관리자)로 감춘다 — 팀 쓰기는 org-service가 GLOBAL ADMIN을 요구하므로 같은 사람이다
- 판정은 서버가 한다. 화면은 403 메시지를 그대로 보여준다

팀 삭제 확인 문구에 "이 팀에 걸린 스페이스 권한도 더는 통하지 않습니다"를 넣었다 — 팀을 지우는
것은 조직도 정리가 아니라 권한 회수다.

## 30. W23 — 스페이스 내보내기 (2026-08-30)

문서 하나(하위 포함)씩만 내보낼 수 있어서 스페이스를 통째로 백업하거나 옮기려면 루트마다
반복해야 했다. 스페이스 설정 → 일반에 **스페이스 내보내기** 판을 뒀다.

- 형식은 문서 내보내기와 같다(Markdown 무손실 · HTML 이미지 내장). 파이프라인을 새로 두면
  확장 문법(패널·컬럼·표 병합)에서 결과가 어긋난다 — 렌더 함수를 문서/스페이스가 공유한다
- 루트마다 후손을 따로 묻는다(루트 수만큼 왕복). 스페이스 전량을 한 번에 주는 API를 다시 두지
  않기 위해서다 — 그 API는 규모 대응(2026-08-29)에서 일부러 없앴다
- 보관함·휴지통의 문서는 빠진다(트리 조회에서 이미 빠진다)
