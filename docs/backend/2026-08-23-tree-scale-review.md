# 트리 구조 DB·규모 확장성 기술 검토 (2026-08-23)

> 요청 배경: "트리 형태로 해서 검색하기 빠르게 하는 기술 검토" + "데이터가 정말로 많을 때랑
> 사용자가 많을 때 고려". 대상은 wiki-backend(page 테이블)와 그 소비자(wiki-front 사이드바
> 트리·검색·협업). **실측 코드 기준**으로 현황 → 대안 비교 → 반영 완료분 → 후속 권고 순.

## 1. 현황 (실측)

- **모델**: adjacency list — `page.parent_id`(자기참조) + `sort_order`(형제 순번, V9).
- **인덱스**: `idx_page_space(space_id)`, `idx_page_parent(parent_id)`,
  `idx_page_group_sort(space_id, parent_id, sort_order, id)` — 형제 그룹 조회는 커버링에 가깝다.
- **트리 API**: `GET /spaces/{id}/pages`가 스페이스 전체 목록을 한 번에 주고 **트리 조립은
  프론트**가 한다(`buildTree`). 계층 질의(재귀 SQL)가 아예 없다.
- **본문 검색**: SQL이 아니라 **search-service**(GraphQL, Redis Streams 이벤트로 색인)가
  담당 — DB 트리 구조와 무관하게 이미 규모 대응 구조다.

## 2. 트리 저장 기법 비교 — 결론: adjacency list 유지

| 기법 | 강점 | 약점 | 판정 |
|---|---|---|---|
| **Adjacency list**(현행) | 쓰기 O(1) — 이동이 `parent_id` 한 칸 수정. 모델 단순 | 계층 질의는 재귀 필요 | ✅ 유지 |
| Closure table | 서브트리/조상 조회 O(1) join | 별도 테이블(N×깊이 행), 이동 시 대량 재작성, 정합성 유지 비용 | ❌ 과잉 |
| Materialized path | 서브트리 = prefix 검색 한 방 | 이동 시 후손 전원의 path 재작성, path 길이 제한 | ❌ 이동 잦은 위키에 불리 |
| PostgreSQL `ltree` | path 계열 중 최적(GiST 인덱스) | 위와 같은 이동 비용 + PG 종속·H2 테스트 스위트와 충돌 | ❌ 현 단계 불필요 |

**근거**: 이 시스템의 지배적 질의는 "스페이스 전체 목록"(트리 API)이고, 그건 `space_id`
등가 조건이라 **어떤 트리 기법으로도 더 빨라지지 않는다**. 계층 질의가 필요한 곳(이동·복제의
서브트리 수집, 순환 검증)은 빈도가 낮고, 스페이스 스코프 1쿼리 + 메모리 BFS로 충분하다(§3).
본문 검색은 search-service 소관이라 DB 트리 기법과 무관. closure/path 계열은 "읽기 최적화를
위해 쓰기(이동)를 비싸게 만드는" 트레이드오프인데, 우리 위키는 드래그 이동·복제가 잦은
쪽이다 — 방향이 반대다.

**전환 트리거**(이게 나타나면 재검토): 스페이스당 페이지 수가 수만 단위가 되어 "전체 목록"
API 자체를 부분 로드(lazy 트리)로 바꿔야 할 때. 그 시점의 권고는 closure가 아니라
**recursive CTE**(`WITH RECURSIVE`) — 모델 무변경으로 서브트리만 DB에서 잘라온다.

## 3. 즉시 반영 완료 (wiki-backend 17b284f)

1. **트리 프로젝션**: 트리 API가 Page 엔티티 전체를 로드해 **모든 문서의 본문 text**가
   스페이스 단위로 전송·역직렬화되고 있었다(최대 낭비 지점 — 문서 1만 개 × 평균 10KB면
   사이드바 한 번에 100MB급). JPQL 생성자 프로젝션으로 트리 7컬럼만 읽는다.
2. **서브트리 N+1 제거**: `collectSubtree`(이동·복제·순환검증)가 노드당 `findByParentId`를
   날렸다 → 스페이스의 `(id, parent_id)` 한 쿼리 + 메모리 BFS. 서브트리는 항상 한 스페이스
   안에 있다는 불변식(이동도 서브트리 단위 스페이스 이전)에 기댄다.

## 4. 데이터가 정말로 많을 때 — 남은 지점과 권고

| 지점 | 현황 | 리스크 | 권고(우선순위) |
|---|---|---|---|
| 트리 API 페이로드 | 제목만(§3 반영 후) | 수만 페이지 스페이스에서 목록 자체가 큼 | P2: lazy 트리(루트+펼친 노드만, recursive CTE) |
| 프론트 트리 렌더 | 전체 노드 렌더 | 1만+ 노드에서 React 렌더 비용 | P2: 가상화(react-window류) — DS 결정 필요 |
| 리비전(page_revision) | 저장마다 전문 스냅샷, 무기한 | 편집 잦은 문서의 무한 성장 | P1: 보존 정책(예: 최근 N + 주기 압축) — **정책 결정 대기** |
| 첨부 | pending 수명주기 있음(V4) | 대용량 파일 자체는 DB 밖(오브젝트 스토리지) | 현행 유지 |
| 댓글·버전 목록 | 페이지 단위 조회 | 페이지당 수천 댓글이면 큼 | P3: 페이지네이션 계약 추가 |
| 검색 | search-service 색인 | DB 부하와 분리됨 | 현행 유지 |

## 5. 사용자가 많을 때 — 남은 지점과 권고

| 지점 | 현황 | 평가 |
|---|---|---|
| 인증 | JWT를 각 서비스가 JWKS 로컬 검증 — 요청당 auth-server 왕복 없음 | ✅ 규모 안전 |
| 인가 | org-service gRPC + Caffeine 30초 캐시, fail-closed 분기 | ✅ (권한 회수 30초 지연은 문서화된 트레이드오프) |
| 동시 편집 | 명시적 버전 낙관락(409) + 협업 모드는 Yjs·Redis fanout(웹소켓 x2 스케일) | ✅ 이미 수평 확장 구조 |

| 읽기 확장 | 단일 PG | P3: 필요 시 읽기 복제 + 트리/조회 계열 라우팅. 지금은 근거(실측 부하) 없음 |

## 6. 하지 않기로 한 것 (반증 기록)

- **closure table / ltree 도입** — §2. 읽기 병목의 실체(전체 목록 API)는 트리 기법과 무관하고,
  이동 비용만 커진다.
- **조회수 Redis 이관** — 원자 UPDATE로 충분한 단계. 측정 없이 인프라를 늘리지 않는다.
- **트리 API 즉시 페이지네이션** — 프론트 트리·검색 필터가 전체 목록 전제. 프로젝션으로
  페이로드를 먼저 줄였고, lazy 트리는 실측 임계(수만 페이지) 도달 시점의 과제.
